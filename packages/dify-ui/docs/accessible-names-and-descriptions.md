# Accessible Names And Descriptions

This contract applies to UI implementation and review in `web/` and `packages/dify-ui/`.
It adapts the [W3C APG naming techniques][apg] to Dify's primitives and application boundaries.
Read the relevant sections when changing labels, descriptions, or visually hidden text.

## Name, Description, And State

The name identifies the control or region; a description adds useful instructions or consequences.
A description is optional when the name is sufficient. For a file action, the name might identify
the operation and file, while the description explains retention or recovery. Avoid repeating the
same sentence in both. See the [name and description computation specification][accname].

Keep state and updates with their existing owners: checked/expanded/disabled semantics belong to
the control, and progress announcements belong to the feature's status or live region. A name or
description attribute alone is not an announcement mechanism. Follow the [Button] loading contract
and [Forms] error relationships.

## Choose The Naming Source

Trace the final DOM element and forwarded props before deciding. Prefer visible text and native
labeling; use an ARIA name when those sources are absent or insufficient. Nearby text is not a
label relationship by proximity alone. The [APG][apg] explains these authoring choices.

| Surface                | Dify choice                                                                                                                                          |
| ---------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------- |
| Text button or link    | Let its meaningful child text name it; do not repeat that name in `aria-label`.                                                                      |
| Form control           | Use the label primitive specified by [Forms], or an associated native `label`. Keep label activation behavior.                                       |
| Icon-only command      | Use [IconButton] with exactly one of `aria-label` or `aria-labelledby` and one decorative glyph hidden from assistive technology.                    |
| Dialog or named region | Reuse its visible title through the primitive's title API or `aria-labelledby`. Use `aria-label` when a name is needed but no suitable title exists. |
| Related control group  | Follow [Forms] and use `Fieldset` with `FieldsetLegend`; preserve each control's own label.                                                          |
| Table or figure        | Prefer `caption` or `figcaption` when a caption is appropriate. See the [APG caption guidance][captions] for name/description differences.           |
| Image                  | Supply meaningful `alt`, or `alt=""` for a decorative image.                                                                                         |
| Plain `div` or `span`  | Keep readable content; do not add `aria-label` or `aria-labelledby` to the default `generic` role.                                                   |

Naming permission comes from semantics, not the presence of an `aria-*` prop. Other roles also
prohibit naming. Do not invent a role merely to permit a label. A plain span may still contain
the text referenced by another element's `aria-labelledby`; that does not name the span itself.
Check [ARIA in HTML][html-naming] for the final element's restrictions.

## Overrides And References

Authoring preference is different from computation priority. A resolving `aria-labelledby` takes
precedence over `aria-label` and normal native/content naming. An empty referenced label can leave
the name empty. A non-empty `aria-label` also overrides normal native/content naming. These sources
are not simply concatenated. The [computation steps][computation] contain the role-specific rules.

- With `aria-labelledby`, reference the intended text directly. Multiple IDs are read in the
  attribute's order; do not build chains of elements that each use `aria-labelledby`.
- Overriding a button or link's content-derived name can suppress meaningful descendant content
  in its accessible representation. Preserve the necessary content in the resulting name.
- Inspect IDs generated by primitives before overriding them. Keep IDs unique across repeated
  rows and simultaneous dialogs, and ensure referenced nodes exist in the relevant open/closed
  and responsive states. Preserve existing description IDs when adding another relationship.
- Do not use `title`, `placeholder`, or Tooltip content as the only naming source. Follow the
  existing [truncated-text disclosure policy][truncation] for native `title` decisions.

## Write Useful Names

Keep the visible label's wording in the accessible name, preferably at the beginning. Add target
context when identical visible actions would otherwise be ambiguous. Matching the visible words
also lets speech-input users invoke what they see. See [WCAG Label in Name][label-in-name].

Use concise action/purpose wording. Avoid appending role words already announced by assistive
technology, or duplicating a state exposed by the control. Application labels and descriptions
use Web i18n keys and the complete localized message; primitives receive text through props and
children and do not import application i18n. Follow [Web contracts][web-contracts].

The following fragments assume localized strings and owner-scoped unique IDs, using `useId`
where needed. This row combines the visible action with the file it affects:

```tsx
<>
  <span id={fileNameId}>{fileName}</span>
  <Button aria-labelledby={`${deleteLabelId} ${fileNameId}`}>
    <span id={deleteLabelId}>{deleteLabel}</span>
  </Button>
</>
```

## Associate Descriptions

Use `aria-describedby` to associate concise help or consequences with a named control. The
referenced content becomes a plain string: headings, lists, and interactive links do not retain
their structure in that description. Keep rich instructions reachable as normal content or
through the [Overlay] contract. `aria-details` may supplement structured content where supported;
it does not replace that reachable content. See the [description attribute reference][describedby].

In Dify fields, compose `FieldDescription` and `FieldError` with the appropriate label and control.
These primitives own their relationships, including invalid-state feedback. Do not overwrite
them with a second label or a competing error association. Within the owning form:

```tsx
<Field name="fileName">
  <FieldLabel>{fileNameLabel}</FieldLabel>
  <Input required />
  <FieldDescription>{formatHint}</FieldDescription>
  <FieldError match="valueMissing">{requiredMessage}</FieldError>
</Field>
```

Use `DialogTitle` and, when useful, `DialogDescription` for a short dialog summary. Do not turn a
whole form or rich dialog body into one description. Tooltip remains supplemental to a named
trigger; essential instructions follow the [Overlay] contract.

Prefer descriptions associated with DOM text. When considering `aria-description`, verify the
target browser and assistive-technology behavior; `aria-describedby` takes precedence rather
than appending it. The [AccName 1.2 working draft][description-computation] specifies this order,
followed by applicable native description sources and unused `title` fallback. Do not stack
description mechanisms to force repeated output.

## Hidden Text And Safe Removal

- `sr-only` hides text visually while retaining it for assistive technology. It can contribute
  to a content-derived name or serve as a referenced label/description. A standalone span does
  not name a sibling control, and `sr-only` is not an automatic replacement for `aria-label`.
- `hidden`, `display: none`, `visibility: hidden`, and `aria-hidden="true"` normally exclude
  content during name calculation. Explicitly referenced hidden nodes can still contribute to
  names or descriptions; inspect the reference and its subtree instead of assuming all hidden
  text is ignored. See the [computation steps][computation] and [description reference][describedby].
- Before removing a label, inspect the resulting name and description in collapsed navigation,
  responsive icon-only layouts, loading, and disabled states. CSS truncation alone does not
  remove the underlying text. Preserve existing primitive relationships and necessary status
  information. Add hidden text only when information would otherwise be missing.
- Verify observable names, descriptions, and keyboard behavior at the changed boundary. Follow
  [Web testing] or [Package testing] for test ownership and scope; for complex naming overrides,
  check the rendered accessibility tree and relevant screen-reader behavior.
