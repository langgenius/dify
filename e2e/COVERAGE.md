# Community journey coverage

This matrix describes executable coverage and the remaining product boundaries. It is not a claim that the current branch has passed CI. Runtime evidence belongs to the workflow run and its Cucumber report.

## Selection and ownership

Cucumber owns scenarios, hooks, and reporting; Playwright supplies browser automation. `scripts/run-cucumber.ts` owns services, seed, execution, and teardown. Keep browser actions in steps and setup/cleanup in the scenario's generated Console client. Do not create a second runner or a parallel handwritten API client for a new feature.

| CI lane                              | Selection                                                                                                       | Environment and evidence                                                                                                                                                                 |
| ------------------------------------ | --------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| PR Chromium full                     | Default functional selection: excludes axe, prepared, external model/tool, Cloud catalog, and skipped scenarios | Community runtime with Agent v2 explicitly enabled; three shards. New core journeys below run here.                                                                                      |
| PR WebKit smoke                      | `@browser-smoke`, excluding skipped scenarios                                                                   | Focused keyboard and navigation coverage, not the full business matrix.                                                                                                                  |
| Post-merge / manual external runtime | `@prepared or @external-model or @external-tool`, excluding skipped scenarios                                   | Strict seed, configured providers, Agent backend and sandbox. Configuration-only prepared scenarios do not themselves call models, but this combined lane requires provider credentials. |
| Manual accessibility                 | Explicit axe level/page selection                                                                               | Automated accessibility audit; not a substitute for functional or keyboard assertions.                                                                                                   |
| Cloud catalog                        | Explicit `@cloud-catalog-runtime` selection                                                                     | Requires a separate initialized Cloud runtime and maintained catalog fixture. Not covered by the Community CI jobs.                                                                      |

`@core` expresses importance, not a runner filter. A scenario tagged both `@core` and `@prepared` belongs to the prepared lane. All scenarios added for the Community journey expansion have an existing CI execution path; do not add dormant placeholders for the backlog.

The core build job also runs `check:scenarios`: a Cucumber dry-run of all non-skipped scenarios, including prepared and external definitions. It checks Gherkin and step bindings without starting browsers or executing hooks. It cannot establish UI correctness, service readiness, or cleanup behavior.

Template workflows use the existing sandbox service. The echo Chatflow uses Start → Answer with the system query and needs no model provider. Each scenario creates disposable resources and registers cleanup before later assertions can fail. Public visitors and Console fixture owners remain separate identities.

## Deferred coverage, in priority order

1. **Agent v2 richer lifecycle:** make the existing prepared duplicate/publication setup scenario-owned instead of mutating a shared seed, then add targeted runtime recovery where a stable contract and environment exist. The seven previously skipped Agent cases are restored in this expansion; CI must verify their seed, UI, and runtime contracts.
2. **Workflow composition and execution:** UI variable references and branch wiring with concrete outputs, failure correction and rerun, and a run's Console log/detail identity. Engine permutations belong in engine tests rather than a browser matrix.
3. **Traditional knowledge:** upload a fixed text file, await indexing, inspect chunks, retrieve a known marker, then disable/delete and verify the retrieval change. Existing seed uses economy keyword indexing without an embedding model, but default core workers consume only `workflow_based_app_execution`; this journey needs dataset queues or a suitable prepared lane before implementation.
4. **App and Chatflow lifecycle:** nontrivial duplication, conversation switching/deletion, inputs and attachments, and published access revocation. Keep the existing Web App disable/restore case.
5. **Human Input:** pause a real workflow, submit as an eligible actor, and prove the original run resumes on the chosen branch. Console, legacy public, and public v2 OTP sessions are separate owners. Mail/IM delivery and pending upload authorization contracts must not be fabricated by test mocks.
6. **Plugins/models/tools and triggers:** fixed plugin installation/configuration through the UI, one controlled tool call, and a real Webhook-triggered run. Third-party provider matrices and schedules require explicit runtime ownership.
7. **Skills and other resource management:** standalone file draft/publication/version restoration, then Agent binding. Lower priority than Agent and traditional application journeys for this expansion.

KnowledgeFS, Cloud network policies, billing, and enterprise governance are not ordinary Community gate candidates. KnowledgeFS requires a supported edition or a Community development override plus its service/capability configuration; do not use that override to claim default CE coverage. Contacts/IM also have feature and delivery prerequisites. Home, tags, profile, and theme should gain browser journeys only when a cross-boundary outcome warrants them.

## Review and validation contract

- State one business rule per scenario; use setup to establish prerequisites, never to perform the operation under test.
- Prefer role/name, label, and intentional test IDs. Do not force clicks, sleep, mutate application stores, or mock Dify responses to manufacture success.
- Register one-shot event waits before the action. Wait for visible readiness or the authoritative persisted contract, with the timeout owned by the actual slow operation.
- Reload to prove persistence; start a fresh run before checking changed output so an earlier result cannot pass the assertion.
- Separate static validation, scenario binding validation, and actual CI execution in PR evidence. In CI-only work, do not run services, browsers, or the E2E suite locally.
- Review failed CI screenshots, HTML, logs, and seed reports before changing locators or timeouts. Do not relax assertions or add skips to obtain a green run.
